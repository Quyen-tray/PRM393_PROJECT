# Employee Workflows: Demo-Ready Design Baseline

**Revision:** 2026-11-03. This revision accepts the owner's conditional approval and resolves decisions D-01 through D-12. It is the design baseline for the implementation backlog.

## Goal

Complete the employee-facing workflows in the existing Flutter and Spring Boot application so they can be exercised against a local backend and demonstrated end-to-end. The current workspace source, API contracts, authorization, and database conventions are authoritative. `SRS_HRM_Coffee_Shop_v2.0.docx` is a reference for business intent; older or undecided policy details do not override current code.

## Source audit

### Existing Flutter behavior

The employee pages use `EmployeeRepository` API calls for dashboard, schedule, profile, check-in/history, checklist, training, rewards, and notifications. `DemoShiftAssignment` and `DemoChecklistTask` are display models populated from API results; the employee pages do not use the static `DemoData` records as their business data source. Attendance already supports device registration, location/photo evidence, check-in/out, adjustment requests, and overtime requests. Checklist already supports assigned runs, item completion, evidence upload, and submission. Training supports catalog, requirements, enrollment, progress/status, and certificate display.

The dashboard links to schedule, checklist, training, profile, notifications, and attendance history; rewards are reachable from profile. There is no employee documents or violations page/route. `/employee/profile` resolves to the real page, while the legacy `/profile` route still resolves to a placeholder. There is a manager violation review page, but no Flutter document review page; the manager dashboard currently has a document-pending summary without a review route.

Flutter tests currently cover authentication routes/logout, manager rewards, admin account pages, a smoke widget, and the error-log integration flows. There are no employee business-flow widget/integration tests yet.

### Existing backend behavior

- `EmployeeDocumentController` already serves `GET` and `POST /api/v1/employees/me/documents`. The employee identity is taken from `SecurityUtils.requireEmployeeId()`. `DocumentService.submit` checks active type, employee-owned private storage key, file existence, dates, and rejects a second `PENDING` document of the same type. It saves a new row, so rejected/expired records can remain as history.
- The employee document-type catalog does not exist. `GET /api/v1/admin/document-types` and position-requirement reads are admin-only. `DocumentService.profile` already calculates mandatory requirements against the employee's current position and effective date, but that result is not an employee document catalog.
- The existing upload endpoint is `POST /api/v1/storage/uploads?purpose=DOCUMENT`. It generates an employee-owned private storage key, validates file signature, accepts PDF/JPEG/PNG/WebP up to 10 MB, and returns the key needed by the existing submit API. The UI must keep that key internal.
- `HrDocumentController` already provides pending queue, approve, and reject APIs protected by `DOCUMENT_REVIEW`. The `STORE_MANAGER` role has this permission; HR is granted it directly in the seed. `SharedDocumentController` provides a protected document detail/view URL. A small Flutter reviewer page is needed to demonstrate this existing approval flow.
- `EmployeeViolationController` currently exposes only employee rewards/penalties; there is no employee violation list or explanation endpoint. `ViolationEvent` has a manager `ReviewNote` but no employee explanation data/table. Manager `GET /api/v1/violations`, `GET /api/v1/violations/{id}`, `POST .../confirm`, and `POST .../dismiss` already exist. List and decisions require `VIOLATION_REVIEW`; the shared detail service permits the employee owner or a reviewer.
- Violation API status mapping is `PENDING -> OPEN`, `APPROVED -> CONFIRMED`, `REJECTED -> DISMISSED`, and `APPLIED -> RESOLVED`. Manager review is only valid while the persisted record is `PENDING`.
- The database source of truth is `hrm-coffeeshop-backend/infra/sqlserver/config.sql`; entities/repositories are generated by `tools/gen_entities.py`. The project has no migration system and maintains only `config.sql` and `seeddata.sql`. Existing databases must not be rebuilt by rerunning those scripts.
- The current seed already includes manager/HR and multiple employee personas, active position document requirements, pending/approved/rejected/expired documents, open violations, and employee demo records. Seeded document metadata refers to `private-documents/seed/...`; real file-preview demonstrations must use newly uploaded files.

## Decisions D-01 through D-12

| ID | Decision |
|---|---|
| D-01 | Add one employee-safe `GET /api/v1/employees/me/documents/catalog` response containing all active document types, the current employee position, effective required/optional flags, and current submission eligibility. The server derives employee and position from the authenticated identity and current effective requirements. If the employee has no current position requirement, active types are optional. |
| D-02 | Block submission when the same employee/type has a `PENDING` document, or an `APPROVED` document that is still valid (no expiry, or expiry today/later). Enforce this in the service and with a database constraint for concurrent pending submissions; map a concurrent duplicate to the same `CONFLICT` response. |
| D-03 | Allow a new document version after `REJECTED` or `EXPIRED`, and after an approved record has expired. Insert a new `EmployeeDocument` row; retain prior metadata and files for audit. Never replace/delete history. |
| D-04 | Derive employee ownership from JWT/security context for document catalog, list, submission, violations, and explanations. Do not accept a client-supplied employee ID for self-service operations. Validate storage keys against the authenticated employee's private namespace. |
| D-05 | Store explanations in a separate append-only `ViolationExplanation` entity/table related to `ViolationEvent` and `Employee`, with explanation text, submitted/created timestamps, and an optional private evidence storage key. Keep it separate from manager `ReviewNote`. |
| D-06 | A submitted explanation cannot be edited or deleted. An employee may add another immutable explanation record while the violation remains `OPEN`; no further submission is allowed after the manager closes the violation. |
| D-07 | Submitting an explanation never changes violation status. The existing manager confirm/dismiss actions remain the only decision transitions. |
| D-08 | Reuse existing `DOCUMENT_REVIEW` document approval APIs and `VIOLATION_REVIEW` violation list/detail/confirm/dismiss APIs. Add only Flutter review presentation and an explanation-read API; do not create parallel manager decision endpoints. |
| D-09 | Keep training assessments, employee test taking, score calculation, and score submission unchanged. Manager/trusted-LMS remains the score authority. |
| D-10 | Use current local/test seed personas first. Add only missing deterministic records to development/test seed data. Demo/test records and accounts must never be enabled in production. |
| D-11 | Use the existing Google sign-in flow for demo. Do not add or use a demo auth bypass. Demo identities must be real Google OAuth Test users mapped to separate Employee A, Employee B, and reviewer accounts in the isolated local database. |
| D-12 | Every changed page/action must show its relevant loading, empty, error/retry, submitting, and persisted outcome states from API data. |

## Documents workflow

### Catalog and submission eligibility

`GET /api/v1/employees/me/documents/catalog` returns all active document types, including optional types. Each item includes `documentTypeId`, `documentCode`, `documentName`, `isActive: true`, `required`, current submission status, `canSubmit`, and a user-safe blocking reason when submission is not allowed. The response includes the current `positionId` and an `asOfDate`. `required` is calculated from the employee's effective position requirements as of the backend business date; when there is no current position requirement, active types remain optional and available.

Eligibility is calculated and enforced server-side:

| Latest applicable state for a type | New submission |
|---|---|
| No document | Allowed |
| `PENDING` | Blocked |
| `APPROVED`, no expiry or not yet expired | Blocked |
| `REJECTED` | Allowed as a new version |
| `EXPIRED` or approved document whose expiry is before the business date | Allowed as a new version |

An expired approval whose maintenance job has not yet set `EXPIRED` is still eligible for resubmission based on its expiry date. Keep all old rows and files. A filtered unique database index must prevent two concurrent `PENDING` rows for one employee/type; a losing concurrent request receives the normal duplicate-submission `CONFLICT` response.

### API and authorization

| Method and path | State | Authorization and behavior |
|---|---|---|
| `GET /api/v1/employees/me/documents/catalog` | New | Authenticated user with a linked employee record; identity from security context; no employee ID input. |
| `GET /api/v1/employees/me/documents` | Existing | Authenticated linked employee; lists own history only. |
| `POST /api/v1/storage/uploads?purpose=DOCUMENT` | Existing | Authenticated linked employee; server generates private employee key; PDF/JPEG/PNG/WebP, maximum 10 MB, signature checked. |
| `POST /api/v1/employees/me/documents` | Existing with lifecycle rule | Authenticated linked employee; accepts type ID, server-generated storage key, issued/expiry dates; no employee ID input. |
| `GET /api/v1/documents/pending` | Existing | `DOCUMENT_REVIEW`; queue metadata for reviewers. |
| `GET /api/v1/documents/{documentId}` | Existing | Owner or `DOCUMENT_REVIEW`; returns a short-lived view URL, not a raw storage key. |
| `POST /api/v1/documents/{documentId}/approve` / `reject` | Existing | `DOCUMENT_REVIEW`; retain existing review validation and rejection reason. |

Add the employee document workflow as the **Hồ sơ** tab in the employee profile experience, with active required/optional types, upload, submission, complete history, and pending/approved/rejected/expired outcomes. A direct `/employee/documents` route may open that tab for dashboard navigation. Add a minimal reviewer page that uses the existing queue, detail/view, approve, and reject APIs. Expose it only to users with `DOCUMENT_REVIEW`; `STORE_MANAGER` and HR can use the existing permission grants. Do not add a `ManagerDocumentController` or duplicate API behavior.

## Violation explanation workflow

### Data and lifecycle

Add `ViolationExplanation` with `ViolationExplanationId` (identity primary key), `ViolationEventId` (foreign key), `EmployeeId` (foreign key), `Explanation` (`NVARCHAR(2000)`, required), `SubmittedAt` (backend clock), `EvidenceStorageKey` (nullable), and `CreatedAt` (database/backend timestamp). Add an index by `ViolationEventId, SubmittedAt`. The service verifies the explanation employee matches the linked violation employee. There is no edit/delete API; every additional submission creates a new row. Record a `VIOLATION_EXPLANATION_SUBMITTED` audit event.

An optional evidence file uses the existing `DOCUMENT` upload purpose and file constraints, with a key owned by the submitting employee. Do not return the raw key. The employee explanation list and reviewer explanation read return a short-lived view URL only after checking owner or `VIOLATION_REVIEW` permission.

### API and authorization

| Method and path | State | Authorization and behavior |
|---|---|---|
| `GET /api/v1/employees/me/violations` | New | Authenticated linked employee; own records only, with existing API statuses. No employee ID filter. |
| `GET /api/v1/employees/me/violations/{violationId}/explanations` | New | Authenticated linked employee; verifies the violation belongs to the current employee. |
| `POST /api/v1/employees/me/violations/{violationId}/explanations` | New | Authenticated linked employee; body has `explanation` and optional employee-owned `evidenceStorageKey`; backend fills employee ID and requires API status `OPEN`. |
| `GET /api/v1/violations/{violationId}/explanations` | New | `VIOLATION_REVIEW`; explanation history and optional signed evidence URLs for the existing reviewer UI. |
| `GET /api/v1/violations`, `GET /api/v1/violations/{violationId}`, `POST .../confirm`, `POST .../dismiss` | Existing | Preserve `VIOLATION_REVIEW`, ownership/self-review checks, and current status transitions. |

Add an employee violations page with status, explanation history, optional evidence, and submission while `OPEN`. Extend `ManagerViolationReviewPage` to show all employee explanations separately from the manager review note. After confirm/dismiss, the employee sees the existing final violation status and cannot submit another explanation.

## Employee navigation and experience

The dashboard's quick access must make these workflows reachable: schedule, attendance/check-in and history/requests, documents, training, checklists, violations/explanations, rewards, notifications, and profile. Add real routes for documents and violations. Redirect the legacy `/profile` route to `/employee/profile` or remove the placeholder route; no employee navigation may land on “Profile - Đang phát triển”.

The reviewer dashboard exposes document review only with `DOCUMENT_REVIEW`; manager violation review remains gated by `VIOLATION_REVIEW`. Preserve existing business statuses from API responses rather than inferring success from a button action. Keep checklist returned/rework state actionable according to the backend's actual status.

## Acceptance criteria

1. A real Google test employee can sign in and reach the seven reference screens—home, check-in, schedule, checklist, training/skills, profile tabs, and notifications—plus violations and rewards. The legacy `/profile` path cannot show the placeholder.
2. Schedule and attendance support the seeded shift; device registration, check-in/out, history, overtime and adjustment request states remain API-backed and recoverable after refresh/error.
3. Document catalog returns only active types with required/optional labels for the authenticated employee's current effective position. Tests cover no document, pending, valid approved, rejected resubmission, expired resubmission, and retained old history. The employee cannot read or submit for another employee or use another person's storage key.
4. A real file upload with PDF/JPEG/PNG/WebP within 10 MB can be submitted; invalid signature/type, over-limit size, missing blob, and duplicate pending submissions are rejected. Employee submits a document; a `DOCUMENT_REVIEW` reviewer views the file and approves/rejects it; the employee sees the persisted outcome and reason.
5. The profile shows personal information, position/work details, and the documents tab; edits only change backend-supported fields. Training course/skill/certificate views, enrollment/progress, and checklist completion/evidence/submission/rework are usable against current APIs. No assessment or score authority behavior changes.
6. Employee A lists only their violations, submits explanation text with optional private evidence, refreshes and sees the explanation while violation status remains `OPEN`; the manager sees the employee text/evidence separately from `ReviewNote` and can use existing confirm/dismiss actions. Employee B cannot read or submit explanations for Employee A's violation. Multiple submissions append; edits/deletes and post-decision submissions are unavailable.
7. Relevant automated backend API/integration and Flutter widget tests cover ownership, status/lifecycle, navigation, upload failures, retry, and manager review. Run the employee workflows on Android emulator with the local backend and a real Google test-user account; report actual results and environment limitations.
8. Demo setup covers two employees and a reviewer with real OAuth test-user identities, deterministic seeded store/shift/checklist/training/document/violation data, and at least one approved, rejected, pending, expired, returned, and retry outcome. Fixtures remain development/test-only.
9. No Git/GitHub operations are part of this work.

## Out of scope

- In-app quizzes, assessment taking, employee score submission/calculation, or changes to the trusted-LMS/manager score authority.
- Payroll functionality, new external services, authentication bypasses, or replacing Google sign-in/device identity.
- New decisions for SRS policies that are not already represented by source/configuration (GPS/face/QR thresholds, retention periods, training shift blockers, financial authority, and payroll policy).
- Broad manager/admin redesign beyond the minimum document reviewer surface and violation explanation display.
- Git/GitHub changes or actions.

## Schema and operational constraints

Update the single DDL source `infra/sqlserver/config.sql`, regenerate the new entity/repository with `tools/gen_entities.py`, and extend `seeddata.sql` only if a required local/demo fixture is missing. There is no schema migration system. Never run either initialization script against a populated database; verify schema changes with the existing fresh Testcontainers database flow. If the currently configured local database must be retained, a controlled schema-update procedure must be agreed before applying it.
